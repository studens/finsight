# Phase `4-pdf-statement` 실행 범위 (리더 확정 계약)

> 이 문서는 core-services / api-routes / frontend 플래너와 qa가 **공유하는 단일 계약**이다.
> 플래너는 이 문서를 벗어나는 설계를 임의로 정하지 않는다. 모순을 발견하면 리더에게 보고한다.

## 목표

기존 CSV 업로드 경로에 **PDF 카드 명세서 업로드**를 추가한다.
PDF 파서가 기존 `ParsedCsv { headers, rows }` 형태로 결과를 내주므로
하위 파이프라인(`maskPii` → 컬럼매핑 → `generateFreeSummary` → Premium 리포트)은 **변경하지 않는다.**

## 리더가 확정한 아키텍처 불변식 (플래너 재량 아님)

### INV-1. PDF 파서의 출력은 `ParsedCsv`다
`src/services/pdf-parser`는 `ParsedCsv { headers, rows, rowCount }`를 반환한다.
`headers`는 파서가 부여하는 **정규화된 한국어 헤더**로 고정한다:

```
["이용일", "가맹점", "청구금액", "구분"]
```

- `청구금액` = D2에 따라 **이번 달 청구액**
- `구분` = `일시불` | `할부` | `연회비` | `해외` | `기타` (category 컬럼 역할)
- 이 헤더에는 이름·주소·계좌·카드번호 컬럼이 **존재하지 않는다.** 따라서 `maskPii`는 제외/마스킹할 컬럼을 찾지 못하는 것이 정상이다.

### INV-2. LLM 컬럼 의미 판정은 업로드 시 **한 번만** 수행한다
`/api/analyze`는 `MaskedRow` 브랜드 불변식(`_workspace/03_api-routes_contract.md` 54행) 때문에 파일을 재파싱한다.
여기서 LLM 판정을 두 번 하면 두 결과가 달라져 **사용자가 본 숫자와 저장된 숫자가 어긋날 수 있다.**

→ `/api/upload`가 판정 결과 `PdfColumnSchema`를 응답에 담아 반환하고,
클라이언트가 기존 `mapping`과 똑같은 방식으로 `/api/analyze`에 되돌려보낸다.
`/api/analyze`는 이 스키마를 **그대로 적용만 하고 LLM을 재호출하지 않는다.**

`PdfColumnSchema`는 구조 메타데이터이며 PII가 아니다(가맹점명·금액 의미 순서만 담는다).

### INV-3. 레댁션 게이트를 통과하지 않은 텍스트는 LLM에 보내지 않는다
표 조각을 Claude에 보내기 직전, 남은 PII 패턴을 검사하는 **차단형** 게이트를 통과해야 한다.
게이트는 경고가 아니라 **예외를 던져 요청을 중단**시킨다.

검사 대상(최소):
- 소계 행에 포함된 실명 (`소계(M614)([REDACTED_REAL_NAME])...` — 실제 문서에서 확인됨)
- 계좌번호 형태(`[REDACTED_REAL_ACCOUNT]`), 카드번호 13~16자리
- 우편번호 5자리 + 주소 키워드(시/군/구/동/로/길/호)
- 전화번호 형태

### INV-4. 원본 PDF·비밀번호 미보관
CSV와 동일하게 PDF 원본은 Storage/디스크/로그 어디에도 쓰지 않고 메모리에서만 다룬다.
비밀번호는 변수로만 전달하고 로그·DB·응답 body·에러 메시지에 넣지 않는다.

### INV-5. 기존 CSV 경로 무회귀
`npm run test`의 기존 테스트가 전부 통과해야 한다. CSV 업로드 흐름의 요청/응답 shape은 바뀌지 않는다.

## API 계약 변경분 (api-routes / frontend 공통)

### POST /api/upload
요청 `multipart/form-data`:
- `file`: CSV **또는** PDF
- `password`: (선택) PDF 비밀번호. PDF가 아니면 무시

성공(200) — PDF일 때 기존 응답에 `pdfColumnSchema`가 추가된다:
```json
{
  "mapping": { "date": "이용일", "merchant": "가맹점", "amount": "청구금액", "category": "구분", "confidence": 1 },
  "sample": { "headers": ["이용일","가맹점","청구금액","구분"], "rows": [...], "excludedColumns": [], "maskedColumns": [] },
  "pdfColumnSchema": { "...": "파서가 판정한 컬럼 의미 스키마 (core-services가 형태 확정)" }
}
```
- CSV일 때는 `pdfColumnSchema`가 **없다**(기존 응답 그대로).

신규 에러:
| 상황 | HTTP | body |
|---|---|---|
| 암호화된 PDF인데 비밀번호 미제공/불일치 | 409 | `{ "code": "PDF_PASSWORD_REQUIRED" }` |
| 레이아웃 해석 실패 / 스캔 이미지 PDF | 422 | `{ "code": "UNSUPPORTED_PDF_FORMAT" }` |

### POST /api/analyze
요청 `multipart/form-data`:
- `file`, `mapping` (기존)
- `password`: (선택) PDF 비밀번호 — 재파싱에 필요
- `pdfColumnSchema`: (PDF일 때 필수) JSON 문자열. upload가 반환한 값을 그대로 돌려보낸다

- PDF인데 `pdfColumnSchema`가 없으면 `400 BAD_REQUEST` (LLM 재판정으로 대체하지 않는다 — INV-2)
- 에러 코드는 upload와 동일(409 / 422 포함)

## 테스트 픽스처 정책 (CRITICAL)

사용자가 제공한 실제 NH농협 PDF에는 **실명·주소·계좌번호**가 들어있어 저장소에 커밋할 수 없다.
다음 두 층으로 나눠 **합성(가명)** 픽스처를 만든다:

1. **파싱 로직용** — 익명화된 좌표 텍스트 아이템 JSON.
   실제 레이아웃에서 관찰된 모든 행 변형을 포함하되 실명/주소/계좌는 가명으로 치환한다.
   파서 단위테스트는 실제 PDF 없이 이 JSON만으로 결정적으로 돌아야 한다.
2. **암호화 경로용** — 내용은 무의미해도 되는 작은 **암호화된 PDF** 1개.
   비밀번호 성공/실패/미제공 3케이스를 검증한다. NH 레이아웃일 필요 없다.

## 실제 NH농협 PDF 분석 결과 (계획 반영 필수)

- 암호화: `/Filter /Standard`, `/V 4`, `/R 4`, `AESV2`, 128bit. 사용자 비밀번호로 열림
- 3페이지: page1 = 청구요약 + **이름/주소/우편번호/결제계좌** (PII 밀집, LLM 전달 금지) / page2 = 거래내역 표 / page3 = 사실상 빈 페이지
### ⚠️ 정정 (리더가 pdfjs-dist 4.10.38로 실제 검증 — 이전 서술을 대체한다)

초기 서술("x좌표로 컬럼 분리 불가, 금액이 하나의 텍스트 런으로 붙어 나온다")은 **다른 라이브러리(pypdf) 기준이었고 pdfjs에서는 틀렸다.**
pdfjs는 금액을 **개별 텍스트 아이템**으로 내주며, 금액 컬럼은 **오른쪽 정렬**이라 `x + width`(right-edge)가 컬럼별로 일치한다.
아래 알고리즘은 리더가 실제 PDF로 **합계 오차 0** 을 확인한 검증된 절차다. **이 절차를 그대로 따르라.**

```
1. pdfjs-dist/legacy/build/pdf.mjs 로 getTextContent()
2. fuzzy y 클러스터링 — |y - clusterY| < 0.5pt 로 같은 행으로 묶는다   ← 필수
3. 행 내 아이템을 x 오름차순 정렬
4. 거래행 판정: 첫 아이템이 /^\d{2}\/\d{2}/
5. 소계/합계 키워드 포함 행 제외
6. 금액 컬럼은 right-edge(= x + width) 클러스터로 식별
7. '청구금액' 컬럼 값 1개를 갖지 않는 행은 제외 (해외이용 섹션이 여기서 자동 탈락)
```

**`0.5pt fuzzy 클러스터링을 생략하면 조용한 데이터 누락이 발생한다.`**
y를 정확히 반올림하면 한 시각적 행이 두 조각으로 갈라진다(실측: 소계 행이 `y=350.33`/`y=350.26`,
합계 행이 `y=312.07`/`y=312.00`으로 분리). 리더가 정확 반올림으로 시도했을 때
**34건 중 24건만 잡히고 합계가 882,646 대신 702,397로 계산됐다.** 이 회귀를 막는 AC가 반드시 필요하다.

실측 right-edge 컬럼 좌표 (NH농협, 거래 34행 기준):

| right-edge | 컬럼 의미 | 등장 |
|---|---|---|
| 275.5 | 이용금액(원 거래액) | 32행 |
| **407.0** | **청구금액 ← D2에 따라 이것만 계상** | 34행 |
| 445.5 | 포인트 | 34행 |
| 558.5 | 할부잔여 | 4행 |

이 좌표값은 **NH농협 고유값이며 하드코딩하면 안 된다.** 다른 카드사는 좌표가 다르다.
→ 코드가 right-edge 클러스터를 **동적으로 발견**하고, **각 클러스터가 어떤 컬럼인지만 LLM이 판정**한다(D1 하이브리드의 정확한 경계).

**검증 골든값:** 위 절차로 NH농협 픽스처를 파싱하면 거래 **34건**, 청구금액 합계 **882,646원**이 나와야 하며
이는 명세서 `합계` 행과 **정확히 일치**한다(오차 0). 할부 건은 청구액만 들어가므로
`03/20 네이버페이_인프런`은 140,252이 아니라 **23,375**로 계상된다. 가명 픽스처는 이 구조를 보존해야 한다.

### 기타 실측 사항

- 날짜는 x≈36.3, 가맹점은 x≈60.0부터 시작하는 별도 아이템으로 존재
- 행 간격은 12.75~12.76pt로 균일
- `PasswordException`이 **두 종류로 구분된다**: `code === 1`(비밀번호 미제공) / `code === 2`(비밀번호 불일치).
  둘 다 409 `PDF_PASSWORD_REQUIRED`로 매핑하되, **프론트는 두 경우의 안내 문구를 다르게** 보여줄 수 있어야 한다
  ("비밀번호를 입력해주세요" vs "비밀번호가 맞지 않아요"). 응답에 비밀번호 자체는 절대 담지 않는다.
- **이미지(스캔) PDF 판정을 "텍스트 아이템 0개"로 하면 안 된다** — 실측에서 마지막 페이지는 푸터만 있어 아이템이 6개다.
  판정 기준은 **문서 전체에서 거래행 후보가 0건**인 경우로 한다.
- 처리해야 할 행 변형 전체:

| 변형 | 실제 관측 문자열 | 주의점 |
|---|---|---|
| 일반+할인 | `06/13이마트24 부산초량점 4,500 53(할인) 4,447 0` | 날짜와 가맹점 사이 공백 없음 |
| 할인 없음 | `06/24아파트관리비 246,090  246,090 0` | 할인 칸이 빈 공백 |
| 연회비 | `06/23기본연회비-올바른BAZIC+카드 6,000  6,000 0` | 지출로 계상(구분=연회비) |
| 할부 | `03/20네이버페이_인프런 140,252 922(면제) 6/4 23,375 0  46,750` | 총액/할인/회차/**이번달청구**/포인트/잔여 → D2에 따라 23,375만 계상 |
| 마이너스 | `06/01포인트결제  -300 0` | 이용금액 칸 자체가 비어있음 |
| 소계/합계 | `소계(M614)([REDACTED_REAL_NAME])올바른BAZIC+카드  866,646 90    277,200`, `합계  882,646 90    277,200` | **거래로 계상하면 이중계상** → 반드시 제외. 실명 포함 → 레댁션 대상 |
| 해외이용 별도 섹션 | `07/03 M614 WWW.ALIEXPRES 룩셈부르크 USD 23.39 ... 36,719` | page2 거래목록의 `07/03 WWW.ALIEXPRESS.COM 36,719`와 **동일 건 중복 표기** → 이중계상 방지 |

- **거래 날짜에 연도가 없다** (MM/DD만). 이용기간 헤더 `[일시불/할부] 2026.06.11 ~ 2026.07.10`에서 연도를 추론해야 한다.
  - 12월→1월 연말 경계 처리 필요
  - 할부 원거래는 이용기간보다 훨씬 과거일 수 있다(`03/20`) → 이용기간 범위 밖이어도 유효한 거래로 취급
- 검증 기준값: 픽스처의 계상 합계가 명세서 `합계` 행과 일치해야 한다(원본 기준 882,646 — 가명 픽스처에서는 대응되는 값)
