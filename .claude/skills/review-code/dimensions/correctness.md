# 차원: 🐛 correctness (정확성·버그)

"이 코드가 의도대로 동작하지 않는 입력/상황"을 찾는 차원이다. 스타일이나 구조는 다른 리뷰어 몫이니 건드리지 마라. **재현 시나리오를 못 쓰겠으면 그 지적은 버려라.**

## 1. 데이터 파이프라인 엣지 케이스 (이 프로젝트의 최대 버그 밭)

CSV → 파싱 → 마스킹 → LLM → 요약 저장 경로는 입력이 사용자 은행/카드사에서 오므로 형식이 제각각이다.

- **인코딩**: 국내 카드사 CSV는 EUC-KR/CP949가 흔하다. UTF-8로 단정하고 읽으면 한글이 깨진다. BOM 처리는?
- **숫자 파싱**: `"1,234,567"`(천단위 콤마), `"₩1,234"`, `"1234.00"`, 음수 표기(`-1000` vs `(1000)` vs `1000원 취소`). `parseInt`/`parseFloat`가 콤마에서 잘려 `1`이 되는 고전 버그.
- **날짜 파싱**: `2026-01-05`, `2026.01.05`, `26/01/05`, `1월 5일`. `new Date(문자열)`은 형식에 따라 `Invalid Date`거나 타임존이 밀린다. UTC/KST 경계에서 하루 밀리는가?
- **빈 값**: 빈 파일, 헤더만 있는 파일, 빈 행이 중간에 섞인 파일, 컬럼 수가 행마다 다른 파일, 값 안에 콤마·따옴표·개행이 든 필드.
- **금액 합산**: 부동소수점 누적 오차, 취소/환불 거래의 부호, 중복 행.
- **컬럼 매핑**: LLM이 매핑을 반환하는데 예상 밖 형식/누락 필드를 주면? 파싱 실패 시 폴백이 있는가, 아니면 500으로 터지는가.

## 2. 비동기·상태

- `await` 누락 — 특히 `Promise`를 반환하는 함수를 `if`나 `try` 안에서 안 기다리고 넘기면 에러가 catch를 빠져나간다.
- `Promise.all`에서 하나 실패 시 전체가 죽는 게 의도인가, `allSettled`여야 하는가.
- 경합: 같은 리소스에 대한 동시 요청(예: 같은 리포트를 두 탭에서 동시 조회 → Premium 리포트 이중 생성). 지연 생성(lazy-generate) 구조는 특히 이 문제에 취약하다 — 중복 생성 방지나 멱등성이 있는가.
- 웹훅은 **중복 전달이 정상**이다(at-least-once). 같은 이벤트가 두 번 와도 결과가 같은가(멱등)? 순서가 뒤바뀌어 와도(구독 취소 후 갱신 이벤트 도착) 상태가 망가지지 않는가?

## 3. 에러 처리

- `catch {}` 로 조용히 삼키는 곳 — 실패가 성공처럼 보인다.
- `catch`에서 로깅만 하고 정상 경로로 계속 진행해서, 뒤 코드가 `undefined`를 만지는가.
- 외부 호출(Claude API, Supabase, Polar)의 타임아웃·rate limit·5xx 처리가 있는가. 없으면 사용자에게 무엇이 보이는가.
- 에러 응답이 실제 원인과 맞는 상태 코드인가(전부 500으로 뭉개고 있진 않은가).

## 4. 일반 로직

- Off-by-one, 경계값(0건, 1건, 최대치), 빈 배열에 `[0]` 접근.
- `null` vs `undefined` vs `0` vs `""` 구분 — `if (value)` 가 `0`이나 `""`를 falsy로 잡아 삼키는가.
- 조건 분기 누락: `if/else if` 체인에 빠진 케이스, `switch`의 default.
- 옵셔널 체이닝 `?.` 뒤에서 `undefined`가 그대로 흘러가 나중에 터지는가(에러 위치가 원인에서 멀어짐).
- TypeScript strict 모드인데 `as`/`any`/`!`로 타입 검사를 우회한 곳 — 우회한 가정이 실제로 성립하는가.

## 5. 테스트로 확인하기

가능하면 **추측을 검증하라**. 전체 스위트(`npm run test`/`typecheck`/`build`)는 메인이 이미 한 번 돌렸으니 다시 돌리지 말고, 의심 가는 함수의 테스트 파일을 읽어 그 엣지 케이스가 이미 커버되는지 확인하거나 그 파일만 지정해 실행한다. 이미 테스트가 잡고 있는 케이스면 지적하지 않는다.
